# RegIntel bug audit — retrieval & reasoning (2026-08-22)

Scope: full read of `regintel/` (rag.py, store.py, prompts.py, llm.py, chunker.py, parser.py), `scripts/ingest.py`, `ui/app.py`, `regintel/api/main.py`. Every bug marked **[reproduced]** was confirmed with a runnable Python reproduction of the exact code, not just by reading it.

The bugs are ranked by how directly they explain the two symptoms you reported: **wrong sources shown** and **wrong reasoning in answers**.

---

## P0 — directly causes wrong/missing sources or wrong answers

### 1. Cross-lingual citation grounding strips *valid* citations wholesale **[reproduced]**

**Where:** `rag.py` — `_is_grounded()` / `cited_sources()` (`_MIN_CITATION_OVERLAP = 0.12`).

**What happens:** the grounding check is pure lexical word-overlap between the claim sentence and the source chunk. Your corpus is mixed-language (KVKK = Turkish, GDPR/DORA = English) and rule 6 forces the answer into the *question's* language. So any cross-language pair fails:

- English question about KVKK → English answer, Turkish sources → overlap ≈ 0 → **every [n] marker stripped, sources panel comes up empty or near-empty** even when the model cited correctly.
- Turkish question routed to GDPR/DORA (English chunks) → same, in reverse.
- Compare mode KVKK vs GDPR asked in English → the whole KVKK column loses its citations.

Reproduction: a correct English 72-hour-notification claim against its real Kurul Kararı 2019/10 Turkish source → `_is_grounded` = **False**. Same claim against the English GDPR Art 33 chunk → True. So the check only works same-language.

**Symptom match:** this looks *exactly* like "wrong sources in the retrieval process" — retrieval was actually fine; the post-hoc verifier silently deleted the evidence.

**Fix options:** (a) skip the lexical check when the claim's language ≠ the chunk's `metadata["language"]` (you already store it — detect answer language with the existing `_TURKISH_CHARS_RE`), keeping only the marker-range check for those; (b) or compute overlap on embeddings (you already have the multilingual model loaded) with a calibrated floor; (c) or translate numerals/dates into the overlap set (they're currently excluded because `_WORD_RE` only matches letters — "72", "saat/hours" never count).

### 2. Turkish İ/I lowercasing breaks BM25 for Turkish text **[reproduced]**

**Where:** `store.py` — `_tokenize()` uses `text.lower()`.

**What happens:** in Python, `"İlgili".lower()` → `"i̇lgili"` (`i` + combining dot U+0307), which is **not equal** to `"ilgili"`. Every word containing İ in the indexed Turkish text (headings like `MADDE`, `BİLDİRİM`, `İlgili kişi`, all-caps section titles from mevzuat.gov.tr) tokenizes to a string that no user query can ever match. Reproduction: query tokens `['ilgili', 'kişinin', 'bildirim', 'hakkı']` vs indexed `BİLDİRİM/İlgili` → only `kişinin`, `hakkı` overlap. The keyword half of your hybrid retrieval is systematically blind to a chunk's most distinctive Turkish terms, so RRF fusion leans on cross-lingual embeddings alone — the exact weakness `extra_query` was added to compensate for.

**Fix:** Turkish-aware fold before lowering: `text.translate(str.maketrans("İI", "iı")).lower()` (and strip U+0307 defensively), applied identically at index time and query time. One-line change in `_tokenize`, then re-run ingest (BM25 is rebuilt in-memory, so just restart — no re-embedding needed).

### 3. `group_sources` merges different legal instruments under one citation label **[reproduced]**

**Where:** `rag.py` — `group_sources()` groups by `(regulation, article_number)` only.

**What happens:** DORA statute Article 5 and RTS 2025/301 Article 5 share the key `("DORA", "5")`. Reproduction: both retrieved and cited → UI shows **one** expander labelled "DORA, Article 5 — ICT risk management framework" containing the RTS's reporting-deadline text inside it. Same collision between any two RTS/ITS documents, and between a Kurul decision item "3" and KVKK Madde 3. The chunk-level `SearchResult.citation` is correct; only the grouped display is wrong — so the user literally sees text attributed to the wrong instrument. This is a *bona fide* "wrong source shown" bug.

**Fix:** group by `(regulation, document_label or "statute", article_number)`. Three-line change.

### 4. API streaming path leaks `<think>` reasoning and never disables it

**Where:** `llm.py` — `ApiLLM.stream_chat()`; config currently has `LLM_PROVIDER = "api"` with OpenRouter qwen3-14b (a thinking model).

**What happens:** `_strip_thinking()`'s own docstring says API hosts need the strip as a safety net because there's no `think: False` equivalent — but only `chat()` applies it. `stream_chat()` yields raw deltas. The Streamlit UI uses `ask_stream`/`compare_stream` exclusively, so with the current provider the user-facing path can (a) display reasoning tokens, (b) burn the 2500-token budget on reasoning before the answer, and (c) run `cited_sources()` over reasoning text, where a stray "[2]" in the thinking gets grounded/stripped against real sources. Also nothing requests reasoning off (OpenRouter supports `"reasoning": {"exclude": true}` / `"enabled": false`).

**Fix:** pass reasoning-off in the request body, and wrap the stream in a small stateful filter that buffers from `<think>` to `</think>` before yielding (also fixes Ollama's stream path for free).

## P1 — wrong reasoning / verification gives false confidence

### 5. Prose-article verifier validated by the *wrong instrument's* article number **[reproduced]**

**Where:** `rag.py` — `_flag_unverified_prose_articles()`, `_REAL_ARTICLE_DOC_TYPES = {"statute", "rts", "its", "delegated_act_draft"}`.

**What happens:** the available-set is `(regulation, article_number)` across all those doc types. A hallucinated prose claim "DORA Article 5" (meaning the *statute*) passes verification because RTS 2025/301's own Article 5 happened to be retrieved. Reproduction confirmed. This is precisely the cross-instrument number collision SYSTEM_PROMPT rule 8 warns the model about — the checker itself commits it.

**Fix:** for a "DORA/GDPR/KVKK Article N" prose mention, only count chunks with `doc_type == "statute"` (an RTS is never cited as "DORA Article N" — it's cited by its own label, which `_PROSE_ARTICLE_RE` deliberately doesn't match).

### 6. KVKK "GEÇİCİ MADDE" articles are never split out at ingest **[reproduced]**

**Where:** `parser.py` — `_TEXT_ART_RE` / `_TEXT_ART_INLINE_RE` only match lines *starting* with `Madde|MADDE`.

**What happens:** `GEÇİCİ MADDE 1-`, `GEÇİCİ MADDE 3-` don't match, so all transitional articles get appended to the body of the last regular article (Madde 32/33 territory). Geçici Madde 3 is the 7499 amendment's transition provision — a topic your corpus specifically curates (`KVKK-7499-AMENDMENT-NOTES`). Questions about it retrieve either nothing or the wrong article with a wrong citation label, and `article_range`/scope notes never know it exists.

**Fix:** allow an optional prefix in both regexes — `^(?:GEÇİCİ\s+|Geçici\s+)?(?:Madde|MADDE)\s+(\d+\w*)` — and label the number as e.g. `Geçici 3` (keep `\w*` group or prepend a marker) so it doesn't collide with regular Madde 3. Re-ingest KVKK afterwards.

### 7. Compound-clause splitter: Turkish markers rarely fire, and when they do the clauses are garbage **[reproduced]**

**Where:** `rag.py` — `_COMPOUND_MARKER_RE` / `_compound_clauses()`.

Two problems, both confirmed:

- Inflected Turkish forms don't match: `"ne kadar sürer?"` fails the trailing `\b` after `ne kadar süre` → only one marker found → no split. The feature silently never triggers for the most natural Turkish phrasing.
- When it does fire, clause boundaries assume English word order (interrogative first). Turkish puts the subject *before* the marker, so: `"TLPT testleri ne sıklıkla yapılmalı ve aktif test aşaması ne kadar süre devam eder?"` → clause 1 = `"ne sıklıkla yapılmalı ve aktif test aşaması"` (lost its own subject "TLPT testleri", swallowed clause 2's subject), clause 2 = `"ne kadar süre devam eder?"` (a bare verb phrase — retrieves nothing useful). Text before the first marker is also dropped entirely in English questions ("Under DORA," etc. — harmless there, fatal in Turkish).

**Fix:** simplest robust variant — split on the conjunction (` ve ` / ` and `) *between* marker positions instead of at marker starts, and prepend the pre-first-marker text to every clause query. Also drop the trailing `\b` on the Turkish stems (`ne kadar s[üu]re\w*`).

### 8. Ollama streaming uses the repeat_penalty value your own comments call harmful

**Where:** `llm.py` — `OllamaLLM.chat()` sends `repeat_penalty: 1.15`; `stream_chat()` sends `1.3`.

The long comment in `chat()` documents that 1.3 was tried and "made things WORSE… incoherent unrelated-vocabulary word-salad." The streaming method — the one the UI uses — still has 1.3, clearly a stale copy. Latent right now (provider is "api"), but the moment you switch back to Ollama, the UI degrades in a way your eval (which calls `ask()` → `chat()` → 1.15) will never detect.

### 9. Your evals don't test the path users run

`scripts/eval.py` and the API use `ask()`/`compare()` (non-streaming: think-stripping applied, penalty 1.15). The Streamlit UI uses `ask_stream`/`compare_stream` (no think-stripping, penalty 1.3, `cited_sources` applied by the caller). So "eval passes, UI misbehaves" is structurally guaranteed whenever a bug lives only on the stream path — which is exactly where bugs 4 and 8 live. Worth fixing as architecture, not just as two patches (see structure options).

## P2 — smaller correctness gaps

**10. GDPR context cue misses curly apostrophes** **[reproduced]** — `_GDPR_CONTEXT_RE` matches `AB'de` but not `AB’de` (U+2019), which is what macOS/Word/phones type by default. The additive GDPR routing you added after the KVKK-only regression silently fails for typographic-quote input. Fix: `['’]` in the pattern (and consider normalizing quotes once, early).

**11. `article_range()` / scope notes include non-statute numbers** — `store.article_range()` filters by regulation only, so Kurul-decision item numbers and RTS article numbers pollute the "statute is indexed from Article lo to hi" claim and the deterministic `_out_of_range_article` denial. Currently benign by luck (no sub-document number exceeds the statute max), but it's the mechanism behind a future false "Article N does not exist." Fix: add `doc_type == "statute"` to the filter.

**12. `_out_of_range_article` misattributes the article number** — it takes the *first* "Article/Madde N" in the question and checks it against the filter regulation. "What does Article 5 of Delegated Regulation 2025/301 say (DORA)?" is checked against base-DORA's range; with a UI filter set to KVKK, a question naming "GDPR Article 45" gets a deterministic "KVKK Madde 45 mevcut değil" style answer. Fix: prefer the regulation named in the question over the filter when they conflict, and skip the check entirely when the question also names a document number (`_DOC_NUMBER_RE` match).

**13. UI shows the raw streamed answer, but stores the cleaned one** — after `st.write_stream`, the visible bubble still contains the markers `cited_sources` later stripped, while the expanders below show only the surviving sources. Until the next rerun the user sees e.g. "[4]" with no source [4] listed — reads as "wrong sources." Fix: render the stream into a placeholder (`st.empty()`), then overwrite it with the cleaned `answer`.

**14. Diacritic-less Turkish defeats the language cue** — `_TURKISH_CHARS_RE` needs ı/ğ/ş, but Turkish users on English keyboards routinely type "veri ihlali bildirimi ne zaman yapilir" — no special chars, no KVKK routing, and the observed GDPR-answers-a-KVKK-question failure returns. Consider a small Turkish-stopword check ("nedir", "hangi", "zaman", "icin"...) as a second cue.

**15. `ingest.py` auto-discovery skips PDFs** — the no-args path globs `.html`/`.txt` only, so `BDDK.pdf` is silently ignored unless named explicitly (the code path for PDFs exists in `ingest()` but is unreachable from discovery). One-line glob fix.

**16. "BDDK" in `REGULATIONS` but not indexed poisons routing** — `_REG_NAME_RE` is built from all config keys, so a question mentioning BDDK auto-filters retrieval to `regulation="BDDK"` → zero chunks → "sources don't cover this," even when the question also touches KVKK ground that *is* indexed. Fix: build the routing regex from `store.regulations()` (what's actually indexed), not from config.

## Structure options

You asked for options on restructuring the project. Ranked by payoff:

**A. One post-processing pipeline for both stream and non-stream paths.** Give `RagPipeline` a single `_finalize(raw_answer, results)` that does think-stripping → script-stripping → prose-article check → citation grounding, and have `ask()`, the UI's stream consumer, and eval all call it. That collapses bugs 4, 8, 9 into one place and guarantees evals exercise what users see. This is the highest-value structural change.

**B. A `text_tr.py` (or `lang.py`) module for language handling.** One place for Turkish-aware lowercasing/casefolding, quote normalization, and language detection — used by `_tokenize`, the grounding check, and the routing regexes. Bugs 1, 7, 10, 14 all exist because language handling is scattered as ad-hoc regexes across three files.

**C. First-class document identity.** Add `doc_id` (the config key) to chunk metadata and key *everything* on it — `group_sources`, the diversity caps, the prose-article verifier, `article_range`. Bugs 3, 5, 11 are all the same root cause: `(regulation, article_number)` is not a unique identity in a corpus with Level-2 instruments.

**D. Split `rag.py` (41KB and growing).** Natural seams: `routing.py` (regulation detection, triage, context-cue regexes + their unit tests), `querying.py` (rewrite, decompose, compound clauses), `postprocess.py` (citation grounding, grouping, prose checks), leaving `rag.py` as the thin orchestrator. Your commit history shows the cue regexes regress repeatedly — isolating them behind a tested module is how that stops.

**E. Data-driven cue lists.** The KVKK/DORA/GDPR context cues and compound markers are hand-tuned regexes that have already caused three documented regressions. Moving them to a small YAML/JSON table (pattern → regulation, with a test file of positive/negative questions) makes each addition reviewable and regression-tested.

# Compare-mode audit (second pass, 2026-08-22)

Compare mode diverges from ask mode in three ways that matter: it bypasses all jurisdiction routing and question decomposition (by design — the user picks both instruments), it runs two independent filtered searches instead of one, and its answer is a **markdown table** rather than prose. Most of the findings below trace back to that third point: every post-processing check in the pipeline was written for prose sentences.

## Verified correct (no bug)

- **Source numbering across the two sides.** `format_sources(results_b, start=len(results_a)+1)` lines up exactly with the 1-based index into `results_a + results_b`, including when side A returns nothing. Tested and pinned in `test_compare_source_numbering_matches_combined_results`.
- **Turkish native-language retrieval.** `_kvkk_native_query` correctly fires on the KVKK side only, in either dropdown order.
- **Diversity caps** apply per side, so one long article can't monopolize a column.

## C1. Citation grounding graded a whole table row instead of one cell — **fixed**

`_marker_claim` treated `.`/`!`/`?`/`\n` as claim boundaries. A markdown table row has none of those between the two regulations' cells, so the "claim" attached to a citation in the KVKK column included the entire GDPR column. Measured on a realistic row: a cleanly-grounded citation's overlap ratio fell from **0.75 to 0.23** (floor 0.12) purely from the opposing cell's words — and the template explicitly asks the model to quote regulatory wording, which is exactly what pushes the diluted ratio under the floor. Cross-lingual pairs are now exempt (P0 fix 1), so this was latent rather than actively firing for KVKK-vs-GDPR, but it would bite on any same-language pair (DORA vs GDPR) and on any long-quote row.

**Fix:** `|` added to the boundary set in `_marker_claim`, so a marker is graded against its own cell.

## C2. Stripping a marker could produce a blank table cell — **fixed**

A cell whose entire content was `[3]` became `|  |` after stripping. `COMPARE_TEMPLATE` explicitly forbids blank columns because a blank cell reads as "this instrument imposes no requirement here" — a substantive claim nobody made. The pipeline was manufacturing exactly the output its own prompt forbids.

**Fix:** `_fill_blank_table_cells()` puts an em dash in any empty table cell (also catches blanks the model leaves itself). Never touches the `|---|---|` separator.

## C3. Unverified-article flag injected English into Turkish answers — **fixed**

`_flag_unverified_prose_articles` replaced an unconfirmed reference with a fixed English string — *"KVKK (a specific article number was not confirmed in the retrieved sources)"* — mid-sentence in an otherwise Turkish answer, breaking SYSTEM_PROMPT rule 6. In compare mode it landed inside a table cell, wrecking the column layout too.

**Fix:** the replacement now matches the mention's own language (`Madde` → Turkish), the same way `_out_of_range_article` already did, and is much shorter.

## C4. Compare with the same regulation on both sides — **fixed**

With one indexed regulation, the UI resolved `reg_a` and `reg_b` to the same instrument (`index=0` and `index=min(1, len-1)` both → 0); a `st.warning` was shown but nothing stopped the run. Users could also pick the same instrument twice from two full dropdowns. The result: the identical filtered search ran twice, every chunk was handed to the model **twice under two different source numbers**, and the model was asked to contrast an instrument with itself — an open invitation to present duplicated text as two differing positions.

**Fix:** `compare()` / `compare_stream()` return a clear language-matched notice instead of running; the UI's B dropdown now excludes whatever A is set to.

## C5. Retrieval manufactures false parity between the two columns — **prompt-hardened**

This is the most consequential compare-mode issue and it is structural, not a coding error.

`MIN_BM25_RELATIVE_SCORE` is relative to *each side's own top match*. So a regulation with nothing relevant to say still contributes a full quota of confident-looking sources. Demonstrated: the GDPR-only concept *"records of processing activities register"* returned three KVKK articles — Information obligation, Breach notification, Administrative fines — none of which address it, at scores (0.402 / 0.395 / 0.301) that look healthy in isolation because they're only ever compared to each other. The model then sees two equally-populated source lists and a template asking for a side-by-side table, and the path of least resistance is to invent a KVKK counterpart rather than write "not covered".

A score-based auto-detector isn't reliable here: with embeddings on, `search()` returns **RRF** scores, which depend only on rank — both sides' top result always scores nearly the same, so cross-side score comparison is meaningless. That's why this is prompt-hardened rather than filtered.

**Fix:** `COMPARE_TEMPLATE` now states plainly that the two lists were retrieved independently, that equal length is not evidence of equal coverage, that off-topic filler means the instrument does not cover the topic, and that a source from one regulation may never be cited in the other's column.

## Open compare-mode gaps (reported, not changed)

- **No instrument binding on citations.** `cited_sources` has no notion of which side a marker belongs to, so a KVKK source cited in the GDPR column passes grounding whenever the provisions are similar — which, for GDPR/KVKK, is most of the time. The information needed to enforce this exists (`results_a` vs `results_b`), but enforcing it requires parsing which table column a marker sits in, which is fragile against column reordering and non-table answers. Now covered by prompt instruction only. **This is the strongest remaining candidate for a real fix** — the robust version is to renumber each side into its own marker namespace (e.g. `[A1]`, `[B1]`) so a cross-column citation is structurally impossible rather than merely discouraged.
- **No compound-question splitting.** `_compound_clauses` is only wired into `_ask_prompt`. An asymmetric compare question ("How does KVKK's Kurul notification differ from DORA's incident classification?") fuses into one shared query used for both sides, diluting each — the same failure that got its own machinery in ask mode.
- **`_out_of_range_article` is not applied in compare mode.** Deliberate-looking and low impact: a compare question naming both instruments makes `_detect_single_regulation` return `None` anyway, and the prose-article verifier still catches a fabricated article number. Left alone rather than adding a deterministic denial path that could fire on the wrong instrument.
- **`top_k_each` is hardcoded to 4** in `compare()`/`compare_stream()` and absent from the API's `CompareRequest`, versus `DEFAULT_TOP_K = 6` in ask mode. With `MAX_CHUNKS_PER_ARTICLE = 2`, four slots per side is thin for a 2–5 row comparison table.
- **Transcript export mangles tables.** `transcript_pdf` renders the answer through `multi_cell`, so a compare answer exports as raw pipe-delimited text. For an audit-facing tool whose main deliverable is the comparison table, this is worth a small markdown-table-to-PDF-table renderer.
